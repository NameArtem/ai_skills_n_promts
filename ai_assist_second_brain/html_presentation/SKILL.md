# Create HTML Deck

Создай полноценную локальную HTML-презентацию с фиксированным дизайн-канвасом 1920×1080, адаптивным подбором под вьюпорт, навигацией с клавиатуры, переносимыми ресурсами и проверкой визуального качества на реальных данных.

## Сохраняй контракт результата

- Поставляй презентацию, а не длинный документ, разбитый на страницы. Каждый слайд должен читаться за несколько секунд и быть полезным, пока кто-то говорит.
- Относись к предоставленным заметкам, скриншотам, spec, handoff и существующим deck как к исходным материалам. Не переспрашивай факты, которые там уже есть.
- Спрашивай только тогда, когда отсутствующее решение может существенно изменить аудиторию, историю, бренд или формат поставки. В остальных случаях озвучь допущение и продолжай.
- Создавай рабочий HTML и ресурсы. Не останавливайся на плане, скриншоте макета или рекомендации по дизайну, если только пользователь не запросил именно этот этап.
- Следи за честностью утверждений и сохраняй работоспособность ссылок на источники. Помечай сомнительный или черновой контент, вместо того чтобы превращать его в ложный факт.

## Выбери путь

- Для нового deck скопируй `assets/deck-template.html` в запрошенное место вывода и замени его примерное содержимое.
- Для существующего deck перед редактированием изучи его HTML, CSS, JavaScript, изображения и текущие скриншоты. Сохраняй его визуальный язык, если только пользователь не попросил редизайн.
- Если пользователь явно требует `.pptx`, используй специализированный скилл для PowerPoint. Не переименовывай HTML в `.pptx`.

## Сначала выстрой историю

1. Определи аудиторию, время выступления, главный тезис, исходные материалы и желаемую концовку.
2. Запиши нарративную основу одним предложением: проблема → изменение → доказательства → вывод. Пусть каждый слайд продвигает её.
3. Дай каждому слайду одну задачу. Предпочитай тезис, сравнение, последовательность, демонстрацию или решение вместо заголовка темы.
4. Держи слайды достаточно лаконичными, чтобы их можно было рассказывать вслух. Переноси объяснения в речь докладчика, а не в ужимание текста.
5. Используй предоставленные скриншоты и диаграммы как доказательства, а не украшения. Обрезай их вокруг обсуждаемой мысли и оставляй ссылки на источники кликабельными, когда это уместно.
6. Не выдумывай метрики, цитаты, возможности продуктов или внешние утверждения. Проверяй нестабильные утверждения, прежде чем помещать их в deck.

Перед реализацией создай компактную карту слайдов с номером слайда, тезисом, доказательствами и предполагаемой визуальной формой. Не превращай эту карту в отдельный результат, если только она не помогает пользователю проверять историю.

## Определи единую визуальную систему

Выбери и используй по всему deck небольшую единую систему:

- две роли типографики и продуманная шкала
- одно семейство нейтральных поверхностей плюс один основной акцент
- одна сетка макета и одинаковые внешние отступы
- ограниченный набор линий, подписей, карточек, диаграмм и рамок изображений
- ясное поведение углов, границ, теней и анимации

Варьируй композицию, чтобы поддерживать историю, а не доказывать, что каждый слайд отличается. Избегай бесконечных одинаковых сеток карточек, декоративных графиков, hero-заглушек на стоковых фото, расплывчатых иконок и бессмысленных градиентов. Отдавай предпочтение типографике, контрасту, выравниванию и паузам как основным инструментам иерархии.

## Сохраняй контракт презентации

Используй эти значения по умолчанию, если у существующего deck нет осознанной альтернативы:

- фиксированный дизайн-канвас 1920×1080
- один автономный HTML-файл плюс соседняя директория `assets/`
- без внешних зависимостей времени выполнения, если это явно не обосновано
- навигация с клавиатуры клавишами-стрелками, Home, End, Page Up и Page Down
- видимый счётчик текущих / всех слайдов
- персистентность текущего слайда через localStorage
- правила печати, показывающие каждый слайд
- минимальная зона клика для элементов управления 44px
- основной текст на дизайн-канвасе 24px или крупнее

Для маленьких экранов центрируй и масштабируй канвас с этой геометрией:

```css
.stage { position: relative; width: 100%; height: 100%; overflow: hidden; }
.deck { position: absolute; left: 50%; top: 50%; width: 1920px; height: 1080px; }
```

```js
const scale = Math.min(window.innerWidth / 1920, window.innerHeight / 1080);
deck.style.transform = `translate(-50%, -50%) scale(${scale})`;
```

Не полагайся на `display: grid; place-items: center` в сочетании с `scale(...)` для deck с фиксированной шириной. Неотмасштабированный блок макета может выйти за пределы вьюпорта ноутбука и обрезаться с одной стороны.

## Используй ресурсы переносимо

- Храни локальные изображения в соседней директории `assets/` и ссылайся на них относительными путями.
- Копируй HTML вместе с его ресурсами при создании копии для рабочего стола или для передачи.
- Добавляй осмысленный текст `alt`.
- Избегай встраивания больших скриншотов как base64, если только явно не требуется однофайловый результат.

## Реализуй полный deck

- Начни со встроенного шаблона для нового автономного deck, затем замени каждый примерный заголовок, футер и плейсхолдер.
- Держи состояние навигации в одном небольшом контроллере и вычисляй счётчик из фактического списка слайдов.
- Сделай элементы управления «назад / вперёд» доступными с помощью мыши, клавиатуры и зон клика размером под палец.
- Добавляй осмысленные заголовки документа и слайдов. Используй семантические заголовки, `aria-hidden` для неактивных слайдов и видимые состояния фокуса.
- Уважай `prefers-reduced-motion`. Держи переходы короткими и функциональными.
- Сохраняй существующий дизайн-язык пользователя при редактировании deck, если только не был запрошен редизайн.
- Держи консоль чистой. Удаляй заброшенные стили, неиспользуемые примерные ресурсы и недостижимые слайды перед сдачей.

## Проверяй перед сдачей

Запусти переносимую проверку структуры:

```bash
python3 <skill-dir>/scripts/check_deck.py /absolute/path/to/deck.html
```

Затем открой deck в реальном браузере и осмотри его. Как минимум протестируй:

| Viewport | Назначение |
|---|---|
| 1512×982 | Полный экран 14-дюймового MacBook |
| 1512×850 | Окно браузера 14-дюймового MacBook |
| 1366×768 | Ноутбук меньшего размера |
| 1920×1080 | Стандартный проектор |

Для каждого вьюпорта убедись:

- прямоугольник deck полностью помещается во вьюпорт
- не появляется полоса прокрутки документа
- первый и последний слайды отображаются корректно
- каждое локальное изображение имеет ненулевой естественный размер
- навигация с клавиатуры доходит до каждого слайда и останавливается на обоих концах
- счётчик слайдов совпадает с фактическим количеством слайдов
- браузер не сообщает об ошибках в консоли или на странице
- элементы управления остаются достаточно крупными и не перекрывают важный контент
- текст остаётся читаемым на обычном расстоянии просмотра ноутбука

Изучай скриншоты в размерах ноутбука и проектора, когда важно визуальное качество. Успешная проверка DOM не доказывает, что переносы строк, плотность или обрезка изображений выглядят хорошо.

Если deck содержит критически важный скриншот, диаграмму, пояснение по наведению или встроенную ссылку, проверь их явно. Если внешние ресурсы неизбежны, протестируй deck один раз при обычном доступе к сети и укажи эту зависимость в handoff.

## Сдача

Верни точный путь к HTML и, если он есть, содержащую его папку, которая должна перемещаться вместе с ним. Укажи количество слайдов, реально протестированные вьюпорты и любые оставшиеся внешние зависимости или оговорки браузера. Если была запрошена копия для рабочего стола, синхронизируй её только после того, как исходная версия пройдёт проверку.
