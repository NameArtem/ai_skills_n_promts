# 5-Whys Root Cause Analysis

Систематическая методика, которая позволяет пробиться сквозь симптомы и вскрыть истинную первопричину проблемы, многократно задавая вопрос «Почему?», пока не выявится фундаментальная причина.

## Когда использовать этот скилл

- Расследование бага, когда очевидное исправление не сработало
- Инциденты в продакшене, требующие постмортем-анализа
- Проблемы производительности с неясным источником
- Повторяющиеся проблемы, которые возвращаются после «исправлений»
- Отказы системы, требующие предотвращения, а не только восстановления
- Любая ситуация, где борьбы с симптомами недостаточно

## Основной процесс

### Фаза 1: Чётко определите проблему

Сформулируйте проблему как конкретный, наблюдаемый факт:

**Хорошие формулировки проблемы:**
- «Время ответа API выросло с 50 мс до 500 мс»
- «Пользователи видят ошибки 500 на странице оформления заказа»
- «Ночной джоб упал в 3:00»

**Плохие формулировки проблемы:**
- «Система медленная» (слишком расплывчато)
- «Что-то сломано» (не конкретно)
- «Пользователи недовольны» (симптом, а не проблема)

**Шаблон описания проблемы:**
```
Что: [Конкретное наблюдаемое поведение]
Когда: [Время/условия возникновения]
Где: [Затронутый компонент/система]
Влияние: [Измеримое последствие]
```

### Фаза 2: Итеративно задавайте вопрос «Почему?»

Для каждого ответа задавайте вопрос «Почему это произошло?», пока не дойдёте до действенной первопричины:

**Цепочка 5 «Почему»:**
```
Проблема: [Описание]
    ↓
Why 1: [Причина первого уровня]
    ↓
Why 2: [Более глубокая причина]
    ↓
Why 3: [Ещё глубже]
    ↓
Why 4: [Приближаемся к корню]
    ↓
Why 5: [Первопричина — действенная]
```

**Проверки качества для каждого «Почему»:**
- Является ли этот ответ фактическим и проверяемым?
- Объясняет ли он предыдущий уровень?
- Есть ли подтверждающие доказательства?
- Может ли на этом уровне быть несколько причин?

### Фаза 3: Определите первопричину

Настоящая первопричина обладает следующими характеристиками:

| Характеристика | Проверка |
|----------------|----------|
| **Действенность** | Можем ли мы что-то с этим сделать? |
| **Предотвратимость** | Предотвратит ли исправление повторение? |
| **Фундаментальность** | Повторный вопрос «почему» не даёт ничего действенного |
| **Проверяемость** | Можем ли мы доказать, что это причина? |

**Условия остановки:**
- Достигнут процесс/политика, которые можно изменить
- Найден отсутствующий контроль или проверка
- Выявлен пробел в знаниях/обучении
- Обнаружен дефект проектирования
- Достигнуто решение об ограничении ресурсов

### Фаза 4: Проверьте цепочку

Двигайтесь по цепочке в обратном порядке:

```
Если [Первопричина] устранена
→ То [Why 4] не произойдёт
→ То [Why 3] не произойдёт
→ То [Why 2] не произойдёт
→ То [Why 1] не произойдёт
→ То [Проблема] не возникнет
```

Если цепочка разрывается в любой точке, пересмотрите этот уровень.

### Фаза 5: Определите контрмеры

Для первопричины определите:

1. **Немедленное исправление** — остановить кровотечение
2. **Профилактическая мера** — гарантировать, что это не повторится
3. **Механизм обнаружения** — вовремя поймать, если профилактика не сработает

## Типичные ошибки

### Ошибка 1: Остановка слишком рано

**Симптом:** первопричина всё ещё является симптомом
```
Проблема: Сервер упал
Why 1: Закончилась память
→ «Исправление: добавить память» ❌ (лечим симптом)

Продолжаем:
Why 2: Утечка памяти в сервисе X
Why 3: Пул соединений не освобождает соединения
Why 4: Обработчик исключений не закрывает соединения
Why 5: В коде базы данных нет блока finally
→ Исправление: добавить правильную очистку ресурсов ✓
```

### Ошибка 2: Поиск виноватых вместо причин

**Неправильно:** «Почему? → Разработчик ошибся»
**Правильно:** «Почему? → Код-ревью не выявило проблему»
**Ещё лучше:** «Почему? → Нет автоматического теста для этого случая»

**Правило:** сосредотачивайтесь на процессах и системах, а не на людях.

### Ошибка 3: Одна ветка, когда причин несколько

Иногда у проблемы несколько способствующих факторов:

```
Проблема: Деплой не удался
    ↓
Why 1: Истекло время ожидания миграции БД
    ├─→ Ветка A: Почему миграция заняла так долго?
    │   └─→ Блокировка таблицы держалась слишком долго
    │       └─→ Долго выполняющийся запрос
    │           └─→ Отсутствует индекс
    │
    └─→ Ветка B: Почему таймаут такой короткий?
        └─→ Использован таймаут по умолчанию
            └─→ Нет конфигурации под конкретный деплой
```

### Ошибка 4: Непроверенные предположения

Каждое «почему» должно подкрепляться доказательствами:

| Уровень | Ответ | Необходимые доказательства |
|---------|-------|----------------------------|
| Why 1 | «Сервис упал» | Логи с крашем |
| Why 2 | «Убит из-за OOM» | dmesg/системные логи |
| Why 3 | «Утечка памяти» | Анализ heap-дампа |
| Why 4 | «Незакрытые потоки» | Инспекция кода |
| Why 5 | «Отсутствует finally» | Git blame |

## Интеграция с другими инструментами

| Инструмент | Когда комбинировать |
|------------|---------------------|
| **First Principles** | Когда сомневаетесь, верна ли сама формулировка проблемы |
| **Hypothesis Testing** | Когда доказательства для «почему» ненадёжны |
| **Pre-mortem** | После исправления, чтобы предотвратить похожие проблемы |
| **Trade-off Analysis** | При выборе между контрмерами |

## Границы

**Будет:**
- Систематически прослеживать проблемы до первопричин
- Гарантировать, что каждый уровень основан на доказательствах
- Выявлять действенные контрмеры
- Обрабатывать деревья причин с несколькими ветками

**Не будет:**
- Останавливаться на обвинениях («человеческий фактор»)
- Принимать расплывчатые ответы без доказательств
- Гарантировать ровно 5 уровней (может быть 3, а может и 7)
- Заменять детальную отладку, когда нужна инспекция кода

## Краткая шпаргалка

**Чек-лист 5 «Почему»:**
- [ ] Проблема сформулирована конкретно и измеримо
- [ ] Каждое «почему» фактическое, а не предположение
- [ ] Каждый уровень подтверждён доказательствами
- [ ] Первопричина действенна и предотвратима
- [ ] Цепочка подтверждается при обратном прослеживании
- [ ] Контрмеры направлены на первопричину, а не на симптомы
- [ ] Фокус на процессе/системе, а не на обвинениях
