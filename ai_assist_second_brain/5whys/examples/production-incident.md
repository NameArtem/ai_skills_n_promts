# Пример: Инцидент в продакшене — отключение платёжного сервиса

Полный анализ 5-Whys отказа платёжного сервиса в продакшене.

---

## Анализ 5 «Почему»: Отключение платёжного сервиса (2024-01-15)

### Описание проблемы

| Поле | Детали |
|------|--------|
| **Что** | Платёжный API возвращает ошибки 503, все транзакции не проходят |
| **Когда** | 2024-01-15, 14:23 UTC, в период пикового трафика |
| **Где** | payment-service в продакшене (us-east-1) |
| **Длительность** | 47 минут |
| **Влияние** | ~$150 000 в невыполненных транзакциях, 12 000 затронутых пользователей |

### Таймлайн

```
14:23 - В мониторинге появляются первые ошибки 503
14:25 - Срабатывает алерт: error rate payment-service > 5%
14:28 - Дежурный инженер начинает расследование
14:35 - Выявлено: все соединения с БД исчерпаны
14:42 - Попытка перезапуска, проблема сохраняется
14:55 - Выявлена первопричина: утечка соединений
15:02 - Развёрнут хотфикс
15:10 - Сервис полностью восстановлен
```

---

### Цепочка «Почему»

| Уровень | Вопрос | Ответ | Доказательства |
|---------|--------|-------|----------------|
| **Why 1** | Почему платёжный API возвращал ошибки 503? | Пул соединений с БД был исчерпан (0/100 доступно) | Метрики пула соединений показали 100/100 занято |
| **Why 2** | Почему пул соединений был исчерпан? | Соединения приобретались, но не освобождались | Гистограмма возраста соединений показала, что соединения держатся часами |
| **Why 3** | Почему соединения не освобождались? | Исключение выбрасывалось до вызова connection.close() в обработчике возвратов | Стек-трейс в логах показал исключение на строке 142 |
| **Why 4** | Почему исключение помешало закрытию соединения? | Нет блока try-finally; close() только в счастливом пути | Инспекция кода RefundHandler.java |
| **Why 5** | Почему не было блока try-finally? | Код скопирован из старого сервиса, который использовал auto-commit (явное закрытие не требовалось) | Git blame показал копипаст из легаси-сервиса |

---

### Первопричина

**Выявленная причина:** код обработки соединений был скопирован из легаси-сервиса, который использовал режим auto-commit (где соединения закрываются автоматически). Новый сервис использует ручные транзакции, требующие явного вызова close(), но паттерн кода не был обновлён.

**Категория:** Пробел в проектировании (некорректное применение паттерна)

**Уверенность:** Высокая (воспроизведено в staging)

---

### Многоветвевой анализ

Отключение усугубил способствующий фактор:

```
Основная ветка (Первопричина):
Утечка соединений в обработчике возвратов
    ↓
Пул исчерпан

Способствующая ветка (усугубила ситуацию):
Почему это не было поймано раньше?
    ↓
Why 1: Нет алерта на мониторинг пула соединений
    ↓
Why 2: Дашборд мониторинга существовал, но не было порога алерта
    ↓
Why 3: Алерт был в бэклоге, не приоритизирован
    ↓
Why 4: Для загрузки пула соединений не определён SLO
```

---

### Извлечённые уроки

1. **Копирование кода рискованно** — паттерны из одного контекста могут не работать в другом
2. **Очистка ресурсов требует защиты в глубину** — линтинг + ревью + мониторинг
3. **Мониторинг без алертов неполноценен** — дашборды не будят дежурных
4. **Пул соединений должен быть видимым** — это метрика первого класса
