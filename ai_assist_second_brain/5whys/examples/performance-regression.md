# Пример: Деградация производительности — рост задержки API

Анализ 5-Whys, прослеживающий деградацию производительности до её первопричины.

---

## Анализ 5 «Почему»: Регрессия задержки Search API

### Описание проблемы

| Поле | Детали |
|------|--------|
| **Что** | p99-задержка Search API выросла с 200 мс до 800 мс |
| **Когда** | Впервые замечено 2024-02-01, после деплоя v2.3.0 |
| **Где** | search-service, все регионы |
| **Длительность** | До развёртывания исправления |
| **Влияние** | Жалобы пользователей, падение использования поиска на 15% |

### Таймлайн обнаружения

```
1 фев, 10:00 - v2.3.0 развёрнут в продакшен
1 фев, 14:00 - Срабатывает алерт задержки (p99 > 500 мс)
1 фев, 14:30 - Начинается расследование
2 фев, 09:00 - Выявлена первопричина
2 фев, 15:00 - Исправление развёрнуто, задержка вернулась в норму
```

---

### Цепочка «Почему»

| Уровень | Вопрос | Ответ | Доказательства |
|---------|--------|-------|----------------|
| **Why 1** | Почему задержка Search API выросла в 4 раза? | Запросы к БД выполняются дольше | Метрики времени запросов показали время БД 600 мс против 100 мс раньше |
| **Why 2** | Почему запросы к БД медленнее? | Полное сканирование таблицы products | EXPLAIN ANALYZE показал Seq Scan вместо Index Scan |
| **Why 3** | Почему происходит полное сканирование таблицы? | Предикат запроса изменился и не использует индекс | План запроса показывает, что индекс по `category_id` не используется |
| **Why 4** | Почему новый запрос не использует индекс? | Новый фильтр использует `LOWER(category_name)` вместо `category_id` | Дифф кода в v2.3.0 показывает изменение |
| **Why 5** | Почему это изменение было сделано без индекса? | Разработчик предположил, что существующий индекс покрывает запрос; ревью запроса не было | В PR #1847 нет проверки плана запроса |

---

### Более глубокое расследование

**Почему в PR #1847 не было ревью запроса?**

| Уровень | Вопрос | Ответ |
|---------|--------|-------|
| Why 5a | Почему нет ревью запроса? | У команды нет чек-листа ревью запросов |
| Why 5b | Почему нет чек-листа? | Производительность не считалась критичной для поиска |
| Why 5c | Почему она не считалась критичной? | Для задержки поиска не определён SLO |

**Вторая первопричина:** нет SLO по производительности → нет процесса ревью → регрессия попала в прод

---

### Первопричины

**Основная первопричина:**
Запрос изменён на использование `LOWER(category_name)` для регистронезависимого поиска, но для этого выражения не существует функционального индекса.

**Категория:** Пробел в проектировании + Пробел в процессе

**Вторичная первопричина:**
В процессе PR нет ревью производительности запросов из-за отсутствия SLO по задержке.

**Категория:** Пробел в процессе

---

### Проверка

| Тест | Результат |
|------|-----------|
| Добавить индекс по `LOWER(category_name)` | Запрос падает до 80 мс ✓ |
| Развернуть со индексом в staging | p99 возвращается к 180 мс ✓ |
| Убрать индекс, вернуть фильтр по `category_id` | Проблема тоже решается ✓ |

**Выбранное исправление:** добавить функциональный индекс (сохраняет регистронезависимую фичу)

```sql
CREATE INDEX idx_products_category_name_lower
ON products (LOWER(category_name));
```

---

### Почему это не было поймано раньше?

| Этап | Должен был поймать? | Почему не поймал |
|------|---------------------|------------------|
| **Код-ревью** | Возможно | Ревьюер не проверил план запроса |
| **Юнит-тесты** | Нет | Тесты не измеряют производительность |
| **Интеграционные тесты** | Возможно | Тестовые данные слишком малы (100 строк против 10M в проде) |
| **Staging** | Возможно | В staging 1M строк, мог бы поймать |
| **Canary-деплой** | Да | Но canary не был включён для этого сервиса |

### Созданный чек-лист ревью запросов

Для любого PR, который изменяет запросы к БД:

- [ ] Запустить `EXPLAIN ANALYZE` на новых/изменённых запросах
- [ ] Проверить использование индексов (нет Seq Scan на больших таблицах)
- [ ] Сравнить оценённое количество строк с фактическим
- [ ] Протестировать с объёмом данных как в проде
- [ ] Задокументировать ожидаемую производительность запроса

---

### Извлечённые уроки

1. **Регистронезависимый поиск требует функциональных индексов**
   - `WHERE LOWER(col) = 'value'` не использует индекс по `col`
   - Нужно создавать индекс по `LOWER(col)`

2. **Объём тестовых данных имеет значение**
   - 100 строк: любой запрос быстрый
   - 10M строк: отсутствие индекса катастрофично

3. **Canary-деплои обязательны**
   - Поймали бы 4-кратный рост задержки при 1% трафика

4. **SLO двигают процесс**
   - Без SLO по задержке никто не приоритизировал ревью производительности
